# Контекст продукта v0 — Analyst Days: моя программа

## Статус и цель
Исходный согласованный контекст для MVP хакатона. Разработка рассчитана примерно на 10–12 часов. Сейчас требуется локальное приложение; публикация на хостинге — отдельный следующий этап. Не создавать внешние аккаунты, не подключать платные сервисы и не публиковать проект без отдельного задания.

## Проблема и пользователь
Пользователь — посетитель Analyst Days. Параллельные доклады затрудняют выбор: участнику нужно собрать личную программу и увидеть накладки по времени.
Продукт позволяет просмотреть программу, выбрать доклады, заметить пересечения и сохранить свой выбор.
Целевой показатель проверки удобства: новый пользователь выбирает три доклада и обнаруживает конфликт за две минуты. Это гипотеза для проверки, а не доказанный результат.

## Основной сценарий
1. Открыть главную и перейти к программе.
2. Выбрать день, просмотреть доклады и подробности.
3. Добавить интересные доклады.
4. Увидеть предупреждение о пересечении.
5. Открыть личную программу и удалить ненужный доклад.
6. Обновить страницу: выбранные доклады сохранились.

## Границы MVP
Включено: главная-лендинг, программа, подробности доклада в диалоге, фильтры по дню и залу, личная программа, добавление/удаление, серверная проверка пересечений, анонимное сохранение, адаптивность, демонстрационные данные.
Не включено: регистрация, админка, оплата, чаты, уведомления, ИИ-рекомендации, импорт, календарный экспорт, офлайн-режим, несколько конференций и интеграция с официальными системами.
При нехватке времени сначала исключить фильтр по залу и декоративные улучшения. Сохранение в БД, отдельный backend и проверку конфликтов не исключать.

## Данные и позиционирование
Название конференции — Analyst Days. Официальная программа пока не предоставлена. Использовать 20 вымышленных докладов на темы анализа, требований, API, архитектуры, данных и ИИ; два дня и три зала; один спикер на доклад.
Показывать: «Демонстрационная программа. Не является официальным расписанием Analyst Days». Не заявлять официальный статус приложения и не использовать вымышленные сведения о реальных спикерах.
Дни в интерфейсе — «День 1» и «День 2». Для воспроизводимого seed использовать условные даты 2030-01-01 и 2030-01-02, не выводить их как реальные даты конференции. Все seed-даты сосредоточить в одном файле. Часовой пояс отображения — Europe/Moscow (UTC+3).
Seed включает полные и частичные пересечения, вложенный интервал, доклады встык и перерыв.

## Бизнес-правила
- Повторное добавление не создаёт дубликат; повторное удаление безопасно.
- Пересечение: A.start < B.end AND B.start < A.end. Доклады встык не конфликтуют.
- Сравниваются полные даты и время, независимо от зала; доклад не сравнивается с собой.
- Конфликт не запрещает сохранение: пользователь решает самостоятельно.
- Все конфликты рассчитывает backend только среди выбранных докладов.
- Выбор сохраняется после перезагрузки страницы и перезапуска сервера.
- Без регистрации программа доступна в том же браузере до истечения сессии или очистки cookie. Срок сессии — 30 дней.
- Данные разных анонимных сессий изолированы.

## Архитектура и репозитории
Frontend: Next.js App Router, TypeScript, Tailwind CSS; shadcn/ui по необходимости.
Backend: Python 3.12, FastAPI, SQLAlchemy 2, Pydantic, SQLite.
Два самостоятельных репозитория: analyst-days-frontend и analyst-days-backend. Разместить рядом в общей папке; не создавать Git-репозиторий в общей папке.
Frontend обращается к /api/* через same-origin proxy Next.js на отдельный backend. Бизнес-логика, сессии и доступ к БД находятся только в backend. Взаимодействие backend с БД — через ORM, не HTTP.
Локальные адреса: frontend http://localhost:3000, backend http://localhost:8000, Swagger http://localhost:8000/docs.

## Документы и источник истины
Этот контекст хранится одинаковой копией в docs/context-v0.md обоих репозиториев.
ТЗ backend — docs/backend-spec.md backend-репозитория; ТЗ frontend — docs/frontend-spec.md frontend-репозитория.
Согласованный контракт API v1 продублирован в обоих ТЗ. При его изменении сначала согласовать изменение и обновить обе копии, затем код. Сгенерированный OpenAPI должен соответствовать контракту.
Не редактировать v0 задним числом для сокрытия изменений: после проверок создать context-v1.md с фактическими выводами.

## Приоритеты реализации
1. Модель данных, seed, API и тесты бизнес-правил.
2. Сквозной сценарий через реальный API.
3. Адаптивность, главная и обработка ошибок.
4. Полная проверка и материалы сдачи.
Агенты работают только в своём репозитории; изменения соседнего репозитория согласовываются. Существующие файлы пользователя не перезаписывать без изучения.

## Критерии готовности
Оба приложения запускаются по README, frontend использует реальный backend, данные сохраняются в SQLite. Конфликты корректны, сессии изолированы. Основной сценарий доступен на телефоне и компьютере. Swagger открывается, проверки выполнены и честно описаны, секретов и базы в Git нет.
