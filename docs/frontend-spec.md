# ТЗ фронтенда — Analyst Days: моя программа

## Задание
Прочитать docs/context-v0.md. Реализовать локальное приложение в analyst-days-frontend и подключить реальный отдельный backend по согласованному контракту. Не менять backend-репозиторий. Не останавливаться на статическом макете.

## Стек и структура
Next.js App Router, TypeScript, Tailwind CSS; shadcn/ui по необходимости. Закрепить совместимые стабильные зависимости и lock-файл. Структура: app/, components/, lib/api.ts, lib/types.ts, docs/.
Одна общая оболочка: навигация «Главная», «Программа», «Моя программа» и счётчик выбора. Русский язык. Не реализовывать бизнес-логику в API routes или Server Actions. Компоненты обращаются через единый API-клиент.

## Экран / — лендинг
Название Analyst Days, заголовок «Соберите свою программу конференции», описание «Выбирайте доклады, замечайте пересечения и держите расписание под рукой». Основная кнопка «Открыть программу», вторичная «Моя программа». Три преимущества и короткий блок «Как это работает». Заметная пометка о демонстрационных данных; не позиционировать как официальный сервис.

## Экран /program
Заголовок «Программа», переключение двух дней, фильтр по залу, список карточек с группировкой по времени начала. По умолчанию первый день и все залы. При смене дня выбранный зал можно сохранить, так как набор залов общий.
Карточка: время начала/окончания, зал, название, спикер, тема, кнопка «В мою программу» / «Убрать из программы». Для выбранного доклада с конфликтом показывать текстовый индикатор.
Название открывает диалог подробностей: полное описание, bio спикера, день, время, зал, тема, действие выбора. Для уже выбранного доклада — список конфликтующих выбранных докладов с названиями и временем. До добавления предварительный расчёт не требуется.
После добавления с конфликтом: «Доклад добавлен. Есть пересечение по времени» и доступный переход к личной программе. Не требовать подтверждения, не блокировать сохранение.
Пустой результат фильтра: объяснение и сброс фильтра зала.

## Экран /my-program
Заголовок «Моя программа», общее число выбранных, число докладов с конфликтами, переключение дня, хронологический список. Использовать ту же карточку и удаление.
Для каждого конфликта: «Пересекается с докладом “Название” — 12:00–12:40, зал B». Название открывает подробности. Список конфликтов брать из API; на клиенте только связывать ID с Talk.
Полностью пустая программа: «Вы пока не выбрали доклады» и кнопка перехода к программе.
Пустой текущий день при выборе в другом: «На этот день доклады не выбраны».
Пояснение: «Программа сохраняется в этом браузере. После очистки данных браузера доступ к ней потеряется. Срок хранения выбора — 30 дней».

## Поведение и состояния
- Сначала выполнить один GET /me/program для инициализации сессии; до завершения действия изменения отключены. Исключить конкурентные первые сессионные запросы, в том числе при React Strict Mode.
- Конференцию и список докладов можно загрузить независимо.
- Общее состояние личной программы должно быть единым для навигации, карточек, диалога и личного расписания.
- PUT возвращает актуальную программу: обновить общее состояние из ответа. После DELETE выполнить GET /me/program.
- Не вычислять бизнес-конфликты повторно на клиенте и не хранить выбор только в localStorage.
- Во время мутации блокировать кнопки изменения программы до завершения запроса, чтобы исключить гонки ответов. Показывать индикатор у активного доклада.
- Использовать пессимистическое сохранение: сначала успешный ответ, затем отметка выбора.
- При сетевой неопределённости показать ошибку и повторно запросить программу перед следующей мутацией. Если синхронизация не удалась, предложить повторить, а не выдавать старое состояние за актуальное.
- Состояния загрузки, ошибки с повтором и пустого результата обязательны.
- При быстрой смене фильтра отменять старый запрос или игнорировать устаревший ответ.
- Даты форматировать явно в Europe/Moscow. Не выводить условные seed-даты как реальные даты конференции.
- Не использовать глобальный серверный кэш для персональных данных.

## Внешний вид и доступность
Светлая основа, контрастный текст, один акцентный цвет. Время и зал заметны. Конфликты обозначаются цветом, текстом и иконкой. Минимум декоративных элементов. Текстовое название Analyst Days достаточно; официальные логотипы не требуются.
Проверить 360, 768, 1440 px; на телефоне одна колонка, без горизонтального скролла. Кнопки удобны для касания. Навигация с клавиатуры, видимый фокус, семантические заголовки, aria-label у кнопок-иконок. Диалог: focus trap, Escape, возврат фокуса. Сообщения о результатах доступны через aria-live.

## Общий контракт API v1

Этот раздел одинаков в двух ТЗ. Имена полей, nullable-поля и формы ответов менять только согласованно.
Все пути начинаются с `/api`. JSON — UTF-8; ID — положительные целые числа. Время — RFC 3339 с обязательным смещением; backend возвращает UTC (`Z`), frontend отображает Europe/Moscow. Для валидации использовать явные response-модели.

### Типы
```typescript
type Day = { id: number; label: string; date: string; sort_order: number };
type Room = { id: number; name: string; sort_order: number };
type Speaker = { id: number; name: string; bio: string };
type Talk = {
  id: number;
  day_id: number;
  title: string;
  description: string;
  topic: string;
  starts_at: string;
  ends_at: string;
  room: Room;
  speaker: Speaker;
};
type Conference = {
  name: string;
  timezone: "Europe/Moscow";
  is_demo: boolean;
  demo_notice: string;
  days: Day[];
  rooms: Room[];
};
type Conflict = { talk_id: number; conflicting_talk_ids: number[] };
type Program = {
  talks: Talk[];
  conflicts: Conflict[];
  selected_count: number;
  conflicting_talk_count: number;
};
type ApiError = {
  error: {
    code: string;
    message: string;
    details: { field: string; message: string }[];
  };
};
```
Все перечисленные поля обязательны, null не используется. Необязательная биография — пустая строка. Пустые коллекции — `[]`.
`Talk` одинаков в списке, подробностях и личной программе; для 20 докладов отдельная сокращённая схема не требуется.

### Методы и ответы
| Метод | Параметры / тело | Успех | Ошибки |
|---|---|---|---|
| GET /api/health | Нет | 200 `{ "status": "ok", "database": "ok" }` | 503 HEALTH_UNAVAILABLE |
| GET /api/conference | Нет | 200 Conference | 500 INTERNAL_ERROR |
| GET /api/talks | Query: необязательные day_id и room_id, целые > 0 | 200 `{ "items": Talk[], "total": number }` | 422 VALIDATION_ERROR |
| GET /api/talks/{talk_id} | Целое > 0 | 200 Talk | 404 TALK_NOT_FOUND, 422 VALIDATION_ERROR |
| GET /api/me/program | Нет | 200 Program | 500 INTERNAL_ERROR |
| PUT /api/me/program/talks/{talk_id} | Целое > 0, без тела | 200 Program после добавления | 404 TALK_NOT_FOUND, 422 VALIDATION_ERROR, 403 ORIGIN_NOT_ALLOWED |
| DELETE /api/me/program/talks/{talk_id} | Целое > 0, без тела | 204, без тела | 422 VALIDATION_ERROR, 403 ORIGIN_NOT_ALLOWED |

Все внутренние ошибки имеют единый формат ApiError. `details` обычно пустой; при 422 содержит безопасные сведения о неверных полях без исходных секретных значений.
Пример 404:
```json
{"error":{"code":"TALK_NOT_FOUND","message":"Доклад не найден","details":[]}}
```
GET /talks для неизвестного положительного day_id или room_id возвращает пустую коллекцию, не 404. `total` — число элементов после фильтрации; пагинации нет.
DELETE возвращает 204 даже если доклада или выбора уже нет. PUT идемпотентен и возвращает актуальную программу при повторе.

### Порядок и конфликты
`days` и `rooms` сортируются по sort_order, затем id. Доклады — starts_at, room.sort_order, id.
`conflicts` содержит только выбранные доклады с конфликтами. Связь симметрична: для A/B присутствуют записи A→B и B→A. ID внутри списка уникальны и отсортированы. Сами записи сортируются по talk_id.
`selected_count = talks.length`; `conflicting_talk_count` — число уникальных докладов, участвующих хотя бы в одном конфликте, а не число пар.
Пустая программа:
```json
{"talks":[],"conflicts":[],"selected_count":0,"conflicting_talk_count":0}
```

### Сессия и транспорт
GET /me/program, PUT и DELETE создают анонимную сессию, если действующей нет. Инициализацию frontend выполняет одним GET /me/program до разрешения кнопок изменения, чтобы не создавать несколько сессий конкурентными первыми запросами.
Backend устанавливает cookie `ad_session`: HttpOnly, SameSite=Lax, Path=/, Max-Age=2592000; Secure по окружению, без Domain. Истечение в БД — фиксированные 30 дней с создания. Не продлевать срок неявно.
Клиент не читает токен и не передаёт session_id. Запросы same-origin `/api/*`, credentials: `same-origin`, cache: `no-store`. Next.js proxy должен передавать Cookie и Set-Cookie.
Все ответы /me/*: Cache-Control: no-store. Origin для PUT/DELETE обязателен и должен совпадать с ALLOWED_ORIGINS, иначе 403. Swagger и curl для мутаций должны отправлять разрешённый Origin явно; это описать в README.

## API-клиент и proxy
Реализовать типизированные методы всех используемых эндпоинтов. Единообразно обрабатывать ApiError и не-JSON сетевые/прокси-ошибки. Не пытаться читать JSON из 204.
.env.example:
```dotenv
BACKEND_URL=http://127.0.0.1:8000
```
Настроить rewrite /api/:path* → ${BACKEND_URL}/api/:path*. BACKEND_URL серверный, не NEXT_PUBLIC. Не вставлять localhost backend в клиентский код. При изменении env документировать необходимость перезапуска Next.js.
Проверить реальную передачу Cookie и Set-Cookie через proxy. Backend ожидает Origin http://localhost:3000 для изменений; frontend открывать именно по этому адресу, а не по альтернативному hostname.

## Проверки
Выполнить production build, TypeScript и линтер. Проверить реальную связку с backend:
1. Открыть программу и подробности.
2. Добавить два пересекающихся доклада; увидеть конфликт и корректные счётчики.
3. Перейти в личную программу и удалить один; конфликт исчезает.
4. Обновить страницу; выбор сохранён.
5. Перезапустить backend с той же БД; выбор сохранён.
6. Новый браузерный контекст имеет пустую программу.
7. Доклады встык не конфликтуют.
8. Отключение backend показывает понятную ошибку и повтор.
9. Проверить фильтры, пустой день, отсутствие дубликатов при быстрых кликах.
10. Проверить мобильную ширину, клавиатуру и диалог.
По возможности автоматизировать один сквозной сценарий Playwright; скриншоты и ручные проверки не выдавать за автоматические тесты. Если backend ещё недоступен, временные моки допустимы для верстки, но итоговая готовность требует реального API; моки не должны незаметно включаться при ошибке сервера.
